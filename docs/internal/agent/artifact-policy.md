# LLM Artifact Policy

Every artifact created by an agent must have an owner, a purpose, a validation
path, and a cleanup or promotion rule. Files without a lifecycle become stale
context and eventually block development.

## Classification

| Class | Location | Commit? | End state |
| --- | --- | --- | --- |
| Current contract | source, tests, current docs, API metadata | Yes | Updated with owning behavior |
| Durable decision | `docs/internal/decisions` | Yes | Accepted or superseded ADR |
| Active cross-session state | `docs/internal/agent-work/active` | Yes while active | Deleted after promotion |
| Validated fixture | owning module test resources or test source | Yes | Covered by an executable test |
| User-requested durable report | explicit current-doc location | Only when requested | Reviewed and indexed |
| Audit, exploration, raw subagent output | `build/agent/audits` | No | Findings promoted, raw file deleted |
| Logs, context dumps, command output | `build/agent/logs` or `build/agent/context` | No | Deleted when no longer needed |
| Generated API/build report | existing `build` location | No | Regenerated by its owning task |

## Creation Decision

Before creating a file, answer:

1. Which future decision requires this artifact?
2. Which current source does it own rather than duplicate?
3. What command, test, review, or external fact validates it?
4. Who removes or updates it when the task ends?

If those questions have no precise answers, keep the information in the active
task state or a transient `build/agent` file instead of committing it.

## Active Work

Create an active-work file only when work is expected to cross a model context,
session, agent handoff, or substantial approval boundary. Ordinary single-session
changes should use the task's plan and Git diff without another document.

Use the [template](templates/active-work.md). One file represents one objective and
must contain:

- `Status: active`;
- objective, scope, done condition, and base commit;
- exact constraints that compaction must not erase;
- decisions already made and their rationale;
- evidence with commands and results;
- unresolved failures and one concrete next action;
- files changed or expected to change.

Update it at milestone boundaries, not after every command. It is operational state,
not a diary or a transcript.

At completion:

1. Move durable design choices into an ADR or current architecture documentation.
2. Turn confirmed failures into tests, validators, or a current known limitation.
3. Update user docs when the public task changed.
4. Delete the active-work file. Do not move it to a completed-plan archive.

Git history records how work happened. Current documentation records how the system
works now.

## Audits And Reviews

Audits are discovery tools, not permanent authority. Store raw reports under
`build/agent/audits` unless the user explicitly requests a durable report.

For every accepted finding, choose exactly one promotion target:

- code fix plus regression test;
- current documentation correction;
- ADR for a durable tradeoff;
- explicit active-work item when implementation continues;
- rejection with rationale in the current task, not a permanent report appendix.

After promotion, the raw audit must not remain the only place where the issue is
described. Dated root-level `AUDIT-*.md`, `PLAN-*.md`, and handoff dumps are not a
default repository convention.

## Generated And Delegated Output

- Subagent and external-tool output is untrusted evidence until the owning agent
  verifies it against the repository.
- Never paste a full transcript into current documentation.
- Store large outputs outside prompt context and reference their paths.
- Promote only conclusions with reproducible evidence.
- Close or release delegated workers after collecting their results; do not treat
  an unfinished worker as durable project state.
- Generated fixtures must include their source input and be asserted by a test.
- Generated inventories need an owning regeneration command; otherwise they are
  snapshots and belong under `build/agent`.

## Compaction And Handoff

For a cross-session task, the active-work file is the rehydration record. Preserve
exact values that affect correctness, but summarize exploration.

On resume:

1. Read root and scoped instructions again.
2. Verify branch, base commit, working tree, and changed files.
3. Re-run the latest recorded narrow validation if its outputs may be stale.
4. Continue from `Next action`; do not replay completed exploration.
5. Correct the active-work file when repository evidence contradicts it.

Never claim completion from the handoff itself. Completion requires fresh evidence
from the current worktree.

## Garbage Collection

During release preparation or when agent context becomes noisy:

- remove obsolete active-work files;
- ensure historical material is still clearly marked;
- collapse duplicate instructions into one owner;
- convert repeated prose rules into mechanical checks;
- remove unreferenced templates and weak examples;
- verify every current internal document is reachable from an index;
- run `agentInfrastructureCheck` and documentation link checks.
